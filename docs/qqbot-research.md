# 结论先行

**可行，且比预想的宽松。** 个人主体（无需营业执照）即可在 QQ 开放平台注册并创建群机器人；核心撮合动作（发布/查询/加入）全部走「@机器人 → 被动回复」链路，被动回复不占额度；通知类（加入提醒、出发提醒、每日播报）走主动消息，额度是**每群每日 1000 条、每用户每日 1000 条**（qpm 限速未认证 30 条/分钟），对百花同行的体量是天文数字。真正的硬门槛只有两个：机器人要**审核上架**（需提交语料、自测报告），以及 **markdown/按钮消息要另行申请**（门槛：上架后过去 7 天平均 ≥3 个群在用——冷启动初期用纯文本即可，不需要它）。

数据来源均为官方文档站 bot.q.qq.com/wiki（api-v2）与 q.qq.com/wiki FAQ，抓取时间 2026-09-13。

# 一、资格与申请路径

- 注册 [q.qq.com](https://q.qq.com/)，主体类型选「个人」；每账号最多注册 **5 个机器人**（企业 10 个），个人主体不能转企业。
- 创建机器人后获得 **AppID + AppSecret**。旧的固定 Token 鉴权已废弃，必须用 **AccessToken**（AppSecret 换取，有时效，需定时刷新）。
- 群机器人**没有公域/私域之分**（那是频道机器人的概念），可直接被拉进普通 QQ 群。
- 上架审核：提交**语料配置（指令词列表）、功能配置、自测报告**；当日 16:00 前提交当日审完。常见驳回：没切回正式环境域名、指令有特殊条件没写进自测报告、审核期间机器人不在线、需要第三方账号绑定但没提供测试账号（对我们=要提供一个可登录的测试学号）。
- 名称要求 ≥2 字、体现功能、禁营销词。「百花同行」可过（与现有品牌一致）。
- markdown/keyboard 按钮能力：上架后**过去 7 天平均使用群数 ≥3** 才能申请，每月 15-20 日统一审核。P0 版本用纯文本完全够。

# 二、接入机制

两种接收事件的方式，二选一：

| | WebSocket（推荐） | WebHook |
|---|---|---|
| 方向 | 机器人**主动外连** wss://api.bot.qq.com/websocket | 平台 POST 我们的 HTTPS 回调 |
| 服务器要求 | 无入站端口，直连即可 | 必须公网 HTTPS（端口 80/443/8080/8443），nginx 加路由 |
| 签名 | 无 | Ed25519 签名校验（secret 派生私钥，event_ts + plain_token） |
| 断线恢复 | OpCode 6 Resume，服务端自动补发漏掉的事件 | 依赖平台重试 |
| 额外运维 | 长连接保活、重连 | 无状态，但要暴露入站端点 |

**推荐 WebSocket**：服务器是国内腾讯云直连 QQ API 没有网络障碍；省掉 nginx 配置与签名实现；Resume 机制保证消息不丢。

握手流程：GET 网关地址 → 连接 → 收 OpCode 10（心跳周期）→ 发 OpCode 2 Identify（鉴权头 `QQBot {AccessToken}`）→ 收 Ready（session_id）→ 按周期发 OpCode 1 心跳。

订阅事件用 intents 位标记，我们只需要 `GROUP_AND_C2C_EVENT (1 << 25)` 一组，覆盖：
- `GROUP_AT_MESSAGE_CREATE`：群里 @机器人 的消息（**核心事件**）
- `C2C_MESSAGE_CREATE`：用户私聊机器人（**绑定流程用**）
- `GROUP_ADD_ROBOT` / `GROUP_DEL_ROBOT`：进群/退群
- `FRIEND_ADD` / `FRIEND_DEL`：加好友（主动私聊的前提，见下）

# 三、消息机制的硬约束（最重要的数字）

**被动消息（回复，带 msg_id / event_id）——不占任何额度：**

| 场景 | 窗口期 | 可回复次数 |
|---|---|---|
| 群聊 | 5 分钟 | 5 次 |
| 单聊 | 60 分钟 | 4 次 |

→ 发布、查询、加入的交互全在这条链路上，@机器人后 5 分钟内最多可追 5 条回复，足够完成「查询→按序号加入→确认」的对话。

**主动消息（不带 msg_id）——有每日额度：**

| 场景 | 每日上限 | 速率（未认证 / 认证） |
|---|---|---|
| 群聊 | 每群 1000 条 | 30 qpm / 60 qpm |
| 单聊 | 每用户 1000 条 | 5 qps 且 30 qpm / 10 qps 且 20 qpm |

→ 群里每天发 1000 条主动消息的上限意味着「每日行程播报」「新行程实时播报」这类功能**毫无配额压力**，真正的限制是 qpm 速率（突发批量提醒要排队/合并）。

**另外三条红线：**
1. 用户可以在 QQ 客户端关闭「允许主动发送」，关了就一律发失败（对应事件 GROUP_MSG_REJECT）——提醒类功能必须容错，不能假设送达。
2. 相同 msg_id + 相同 msg_seq 重复发送会失败；对同一条消息多次回复要**递增 msg_seq**。
3. 消息发出 2 分钟内可撤回（DELETE 接口）——可用来自动撤回格式错误的引导消息。

**接口：** 群聊 `POST /v2/groups/{group_openid}/messages`；单聊 `POST /v2/users/{user_openid}/messages`。msg_type：0=文本，2=markdown（需申请）。图片等富媒体走单独的上传媒体接口再引用 media_info。

# 四、身份与绑定（整个方案的前提）

- 官方机器人给的是 **openid 假名体系**：机器人在群里拿到的用户标识是 `user_openid`（加密假名，不可反查 QQ 号），群本身是 `group_openid`。这与 User 表早已预留的 `qqOpenId` 字段设计完全吻合（建库时就按「QQ 官方机器人后续接入」预留了唯一索引）。
- **绑定流程设计**（私聊完成，避免学号暴露在群里）：
  1. 用户在群里 @机器人 发「绑定」→ 机器人被动回复引导，并主动发起加好友（或用户直接加机器人为好友）；
  2. 私聊发送「绑定 学号」→ 服务端复用现有 `/api/auth/send-code` 的全部逻辑（学号校验、60s 冷却、15m/5 限流、SMTP 发码）发验证码到北化邮箱；
  3. 用户私聊回复 6 位验证码 → 校验通过 → `User.qqOpenId = user_openid` 落库，此后该 QQ 身份即映射到既有北化身份；
  4. 同一邮箱已绑定其他 qqOpenId 时拒绝（唯一索引兜底）。
- 绑定是**一次性动作**，之后群里所有指令直接以 openid 反查 User，无需再登录。网页端与 QQ 端共用同一条身份记录——联系方式、ID、行程全部互通。
- ⚠️ 一个需要实测确认的细节：同一用户在不同群里的 user_openid 是否一致。若不一致，绑定记录要存「user_openid + 绑定时的群」或在 C2C 场景绑定（C2C 的 openid 更可能全局稳定）。开发第一周用沙箱群实测。

# 五、架构设计（只保留一份撮合实现）

```
QQ 群 → QQ 官方服务器 ⇄ (WebSocket) ⇄ qqbot.js（pm2 新进程，3101 不占）
                                        │ 解析 / 会话 / 回复
                                        ▼
                              server.js 内部接口 /api/internal/*（内网 + 管理密钥）
                                        │ 全部业务规则仍只在此实现
                                        ▼
                                   MongoDB（bhtxweb）
```

- **qqbot.js 是薄壳**：只做事件接收、自然语言解析、会话状态（如「查询结果序号→行程 id」的 5 分钟内存缓存）、组装回复文本。它**不直接读写业务集合**，所有撮合动作调 server.js 新增的内部接口（用内网地址 + ADMIN_KEY 鉴权），发布/加入/退出的限流、防超卖、同时 ≤2 等规则天然复用，不产生并行逻辑。
- server.js 需新增内部接口（约 3 个）：`/api/internal/qq/bind-start`（发码）、`/api/internal/qq/bind-check`（校验+落 qqOpenId）、`/api/internal/qq/command`（发布/查询/加入/退出，内部按 openid 执行，复用现有 handler 逻辑抽出的公共函数）。
- pm2 第 5 个应用 `bhtx-qqbot`（fork 模式，同款坑：cluster 不传 node_args）。

# 六、自然语言解析（P0 用规则，不引 LLM）

用户示例「明天下午四点 北化北区到北化东区」解析为 `{date, time, from, to}`：

- **时间**：日期词（今天/明天/后天/大后天/周X/本周X/下周X + 具体日期 MM月DD日）+ 时刻词（X点/X:30/X点半/X点XX分 + 上午/中午/下午/晚上偏移，下午四点=16:00，缺省时刻视为无效并追问）。过去时刻回复提示。
- **地点**：以「到/至/→/－」切分，两段分别去 LOCATIONS 地点库（17 个站点点位前端已有）做精确匹配；匹配失败的高频处理：先尝试去「北化」前缀/别名映射（如「学校」→北化北区），仍失败则回复「未收录该地点，请到网站发布」——地点库不开放自定义，保证「线路×时段」数据质量，这与运营策略（时空切分）一致。
- 解析失败一律回引导文案（合法指令示例），不做模糊猜测。
- 查询语义：「明天 去南站的」「查 周五 北化北区」→ 复用大厅过滤逻辑（日期 + 出发地/目的地），文本列表返回前 5 条 + 剩余条数提示。

规则版覆盖 90%+ 真实场景且零依赖零幻觉；若未来上 LLM 增强（多意图/口语容错），只替换解析层，架构不变。

# 七、功能清单

**P0（上架即用，全被动链路 + 文本消息）**
1. 绑定（见第四节）
2. 发布：「@百花同行 明天下午四点 北化北区到北化东区」→ 解析 → 回复「已发布：9月14日 16:00 北化北区→北化东区，已存联系方式将被采用」（QQ 渠道发布时 contact 取 User.contact，没有则提示去网站补充）
3. 查询：「@百花同行 查 明天」→ 当日行程列表（序号+时间+路线+空位）
4. 加入：「@百花同行 加入 2」→ 按最近一次查询结果的序号加入（5 分钟会话有效期）
5. 我的：「@百花同行 我的」→ 我发起的/我加入的进行中行程

**P1（主动消息，额度充裕但要容错用户关闭通知）**
6. 加入/退出通知：有人加入行程 → 私聊提醒发起人（单聊主动，每用户每日 1000 条内）
7. 出发提醒：定时扫描出发前 1 小时的行程 → 逐个私聊全车成员（qpm 限制下做合并排队）
8. 每日群播报：每天固定时刻把当天行程汇总发到群（群主动 1 条/天）
9. 新行程播报：有人发布行程即向群播报一条（驱动「群里约定时间点集中发布」的冷启动打法）

**P2（数据积累后）**
10. 行程完成后的费用回收提醒（actualCost 填写引导）
11. 热门路线播报（周统计，为「线路×时段专群」运营提供依据）
12. markdown 卡片 + 按钮（加入/退出按钮化），届时已满足「7 天 3 群」门槛可申请

# 八、上线路径与风险

**操作顺序**：q.qq.com 个人主体注册 → 创建机器人「百花同行」→ 拿 AppID/AppSecret → 沙箱群开发联调（沙箱群可自主创建）→ 提交语料+自测报告上架审核（提供测试学号）→ 正式群启用。
**开发量评估**：qqbot.js（WS 接入+解析+会话）+ server.js 内部接口（3 个）≈ 2-3 个工作日的量，无新依赖负担（axios/ws 已有或加一个 ws 包）。
**风险清单**：
- 审核驳回（最高频）：对照官方驳回清单自查——自测报告要写全每个指令的触发条件。
- 主动消息送达率：用户关闭「允许主动发送」即不可达 → 提醒类功能定位为「锦上添花」，关键信息仍以网站为准，不承诺通知。
- openid 语义（第四节实测项）。
- 官方政策变动：qpm/额度数值以开发当时官方文档为准（本文数字抓取于 2026-09-13）。
- 与 Amadeus 的边界：Amadeus 走的是另一套通道（无对外 API，无法复用），本方案是官方 bot 体系，两者互不干扰；群里长期共存时注意指令词区分。
